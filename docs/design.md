# 設計メモ

## 目的

Bluesky アカウントへ、本人の手動投稿とは別に、決まった内容を
1日9回自動投稿する。対象は投稿のみ。内訳は挨拶4回（08:00
おはよう／12:00 こんにちは／19:00 こんばんは／22:00 おやすみ）、
ミニゲーム開発中の宣伝2回（10:00／16:00、URL付き）、ゲーム案
募集3回（09:00／20:00／01:00、URL付き、挨拶行つき）で、時刻は
全て JST。文面はユーザーが指定した固定文で、プレースホルダ展開は
使わない（設定側の仕組みとしては残してある）。

## 構成

- `bot/template.py` — 純粋ロジック。テンプレート展開（日付・曜日）、
  文字数検証（上限300。len() はコードポイント数で書記素数以上に
  なるため安全側の判定）、リンク用 facets の生成（UTF-8バイト位置）。
- `bot/state.py` — スロット単位の同日二重投稿ガード（JSONファイル、
  キーは `日付:スロットID`）。GitHub Actions はファイルシステムが
  揮発するため、これは補助的な防御。本命の防御はサーバー上の
  最新100投稿と枠の時間帯の照合。照合失敗時は送信を止める。
- `bot/bsky_client.py` — AT Protocol の最小クライアント（標準
  ライブラリのみ、依存なし）。createSession でログインし、
  com.atproto.repo.createRecord で app.bsky.feed.post を作る。
  レコード生成は純粋関数 build_post_record に分離。
- `bot/post_daily.py` — CLI。dry-run 既定（無指定なら全スロットの
  文面を表示）。`--due` は直近2時間の未投稿枠を古い順に回収する。
  日付をまたいでも元の枠の日付を使い、予定前と期限切れの枠は送らない。
  実投稿は `--post` ＋ `--slot` または `--due` ＋ `POST_ENABLED=true`
  ＋ 認証情報2点が揃った時だけ。
- `config/post.json` — スロット定義（`id`／`time_jst`／`template`）。
  文面は固定文（後述）。
- `.github/workflows/daily-post.yml` — 毎時03・13・23・33・43・53分に
  `--due` を実行。通常は予定の約3分後に投稿し、起動を取りこぼした
  場合は次回に回収する。投稿ジョブは同じ concurrency グループで
  直列化し、実行上限は5分。手動実行時は全枠プレビュー・直近の枠・
  個別枠と dry-run を選べる。`POST_ENABLED` がキルスイッチ。
- `.github/workflows/keepalive.yml` — 月1回（毎月1日 12:17 JST
  目安）空コミットを1つ push するだけのワークフロー。公開
  リポジトリでは60日間リポジトリ活動がないとスケジュール実行が
  GitHub に自動無効化され、ワークフローの実行自体は活動に
  数えられないため、コミットで活動を途切れさせない。
  `contents: write` 権限が必要で、初回は手動実行で push が
  成功することを確認する。

## 文面について

初期設計では日付・曜日プレースホルダで毎日文面を変える想定だったが、
2026-10-29 にユーザーが全スロット分の固定文を指定したため、
プレースホルダは使っていない（仕組み自体は template.py に残置）。
Bluesky は X のような重複投稿の拒否をしないため、同じ文面の
毎日投稿でも技術的には投稿できる。

## X 版との違い

- 課金なし（X は投稿ごと従量課金、URL付きは割高）。
- 認証は OAuth 1.0a の4点セットではなく、ハンドル＋アプリ
  パスワードの2点。アプリパスワードは単独で失効できる。
- 文字数上限は300（X の重み付き280ではない）。
- URL は facets を付けないとリンクにならない（X との大きな違い）。

## リスクと対策

- アカウントへの影響： Bot の不具合はそのまま投稿として出る。
  → 文面は設定ファイル固定、生成 AI で文を作らない。予定は1日9枠。
  過去2時間だけを回収し、長時間停止後の古い枠の一斉投稿は避ける。
- 認証情報の漏洩： → アプリパスワード＋Secrets / .env のみ。
  本体パスワードは使わない。コードと文書に実値を書かない。
- レート制限： 書き込みは 5,000 ポイント/時・35,000/日（作成=3）。
  1日9件でも27ポイントで、到達し得ない。
- 投稿頻度： 宣伝・募集が1日5件と多めなので、止めたくなったら
  `POST_ENABLED` で即停止できるようにしてある。文面はユーザー
  指定の固定文で、自動投稿の表記は入れていない（2026-10-29決定）。反応を見て頻度を落とす場合は、ワークフローの
  config/post.json のスロット定義を減らせばよい。
