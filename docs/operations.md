# 自動起動・外部からの補助起動・監視

## 構成

- GitHubの通常予約：毎時03・13・23・33・43・53分。予定から2時間以内の未投稿枠を処理する。
- 外部の補助起動：Museが、所有者Arbeit2025の権限で運用Issue #2の `external_tick_utc` を更新する。`issues: edited`を受けたdaily-postが同じ処理を行う。
- 状態の保存：Issue #2のhealth関連の状態（`health`、`last_health`、`last_notified_code` など）の外部更新担当もMuseだけとする。
- 独立監視：ChatGPTの毎時タスクはGitHubの実行履歴・実行結果とBlueskyの公開投稿を読む。Issue #2への保存・補助起動は行わない。通常予約が30分以上止まった場合、両方の起動経路が90分以上止まった場合、予定から30分経っても公開投稿がない場合を区別する。

補助起動の定期実行はMuse側の実行基盤で設定し、ChatGPTの独立監視はChatGPTのタスク基盤で行う。リポジトリ内の担当指定だけでMuse側の定期設定が作成・有効化されるわけではない。Muse側の有効状態・実行間隔・次回実行予定はMuse自身が確認する。ChatGPTの監視は1時間間隔で、閾値を超えた直後の通知や秒・分単位の定時起動を保証しない。GitHub Actions全体が停止した場合は外部起動でも実行できず、監視から異常を知らせる。

外部起動には新しい個人アクセストークンやBluesky認証情報の移し替えを使わない。GitHubの既存SecretsはGitHub内の実行だけで使用する。Issue本文には公開してよい運用時刻と状態だけを保存する。

## 担当範囲（2026-10-29のユーザー指定）

| 対象 | 担当 | 許可する操作 |
| --- | --- | --- |
| 外部tick・補助起動 | Muse | Issue #2の `external_tick_utc` の更新 |
| Issue #2の運用状態 | Muse | health関連の状態の保存、前回通知コードの更新 |
| 独立した稼働監視 | ChatGPT | リポジトリ・Actions・公開投稿の参照と、通常のタスク通知 |
| 通常の予約投稿 | GitHub Actions | 既存scheduleによる実行 |

ChatGPTはIssue #2の本文・タイトル・ラベル・担当者・開閉状態・コメントを一切変更しない。別のIssueやファイルへの状態保存、`workflow_dispatch`、再実行などを代替の補助起動経路として使わない。前回通知との比較にはChatGPT自身のタスク実行履歴だけを使う。

この一本化は外部のtick・Issue #2の状態更新に適用する。通常のGitHub Actionsの予約や、別途依頼されたコード開発の担当をMuseだけにするという意味ではない。Issue #2の説明文や過去の開発記録にChatGPT更新の旧手順が残っていても、現在の担当方針を優先する。

同じGitHub所有者アカウントを使う場合、GitHubの編集者名だけではMuseとChatGPTを識別できない。既存の所有者チェックは維持し、Muse単独運用は各AIの実行指示で守る。文書の反映とMuse側の実稼働確認は区別し、[引き継ぎの確認](watchdog-task.md#引き継ぎの確認)を満たすまでは実稼働を確認済みとしない。

## 外部起動の制限

- 対象リポジトリとIssue番号は固定。所有者が作成した開いているIssue #2の本文を、所有者本人が編集した場合にだけ許可する。
- 一般のIssue・第三者の操作・タイトルだけの編集・閉じたIssueは投稿処理へ進まない。
- Issue本文をコマンド、投稿文、投稿時刻、接続先、認証情報として実行・利用しない。
- 投稿ジョブは起動元を問わず同じconcurrencyグループで直列化する。重複防止はサーバー照合を併用する。
- 2時間を超えた古い挨拶は再生しない。長時間停止からの再開時に古い投稿を大量送信しない。

## 結果の確認

daily-postの各実行で、ActionsのSummary、ログの`BOT_REPORT_JSON=`、7日間保存するJSON artifactに結果を記録する。

| 結果 | 意味 |
| --- | --- |
| posted | 新しく投稿し、公開URIを取得した |
| already_posted | ローカル状態またはサーバー照合で投稿済み |
| no_due | 今は直近2時間内の対象枠がない |
| dry_run | 投稿しない確認実行 |
| disabled | POST_ENABLED=falseによる意図的な停止 |
| configuration_error | 投稿スイッチ未設定・不正な値・不正な選択など |
| missing_credentials | 必要なSecretsが未設定 |
| authentication_error | APIの401・403 |
| api_error | API・通信・照合の失敗 |
| state_read_error | 状態の破損・型違い・読込失敗。投稿前に停止 |
| state_preflight_error | 投稿前の状態保存先チェックに失敗。投稿せず停止 |
| state_write_error | 投稿は存在するが、補助状態の保存に失敗。再実行はサーバー照合が必要 |
| ignored_event | 許可されていない外部イベント |

設定不足は緑色のdry-runとして扱わず失敗終了する。明示的な停止はdisabledとして正常終了するが、投稿成功件数に数えない。手動のallは常にプレビューで、既定のdry_run=trueも維持する。

## 投稿しない本番接続確認

Actionsの「check-access (read only)」を手動実行すると、既存のSecretsで認証し、自分の最近の投稿を読み取る。投稿作成APIは呼ばない。トークン・パスワードは出力しない。

## 外部監視の判定

`config/operations.json`の監視開始時刻以降の枠を判定し、それより前の未投稿を新しい事故として数えない。日付またぎにも対応する。公開フィードの取得エラー・ページ不足は「確認不能」とし、正常と扱わない。

```bash
python -m bot.health --runs-json runs.json --feed-json feed.json \
  --execution-json latest-bot-report.json --output health.json
```

入力はGitHubのworkflow runs APIのJSON、BlueskyのgetAuthorFeedのJSON、最新の実投稿経路のBOT_REPORT_JSON。公開フィードにcursorがあり、必要な時刻まで取得できていない場合は追加ページを取得し、feed配列を連結してcursorを外してから判定する。APIエラーを空配列へ置き換えない。

- healthy：今回観測した範囲で異常なし。
- degraded：GitHubの通常予約が止まっているが、外部経路は稼働。
- unhealthy：未投稿、両経路の停止、実行エラーなど。
- disabled：意図的に停止。
- unknown：取得や判定に失敗し、確認不能。

投稿成功とテスト成功、外部起動成功と通常予約の復旧は、それぞれ区別して運用記録へ残す。

監視はqueued/waiting/pendingを起動済みに数えず、run_started_atがあれば実際の開始時刻で判定する。10分を超える実行中のジョブも異常候補として扱う。公開投稿はexpected_didとauthor.did・URIのDIDが一致するものだけを照合し、リポストと自分のピン留め投稿を区別する。expected_didは2026年10月29日に公開プロフィールで確認した値を設定した。

監視に渡す実行結果は、自動投稿経路のsource/mode、時刻、終了コード、outcomesとcountsの一致を確認する。90分を超えた結果、読み取り専用診断の結果、不明な状態、停止とエラーの混在を正常判定に使わない。正当な停止はdisabledの固定通知コードを返す。監視開始時刻が未来になっていたら確認不能として扱い、猶予期間が永久に続く状態を防ぐ。

状態JSONは不存在だけを初回状態とし、破損や読込失敗は空に置き換えない。送信前に保存先へ一時ファイルを作れることを確認し、保存は同じディレクトリの一時ファイルへ書込・flush・fsync後に置換する。置換前の失敗では元の状態を保持する。投稿後に新しいI/O障害が起きる可能性は残るため、サーバー側の照合も引き続き必要。

設定は全枠を実行前に検証する。slotsは空にできず、IDと予定時刻はそれぞれ一意にする。同時刻へ複数枠は設定しない。時刻はHH:MM、IDは英字で始まる1〜64字のASCII英数字・_・-。文面の置換はdate・date_ja・weekday_ja・slot_timeだけで、書式指定・属性参照は使わない。文字どおりの波括弧は{{と}}で表す。未知の置換名、不正なタイムゾーン、展開後に空または300文字を超える文面は投稿前に停止する。

random_slotsは任意キーで、固定枠とは別に「窓の中のランダムな時刻に1日数件」を表す。窓（window_start_jst/window_end_jst）は15分境界で幅は15分の倍数とし、IDは固定枠とも重複させない。1日の回数はtimes_per_day（省略時1、最大8）で、窓をその回数分の等しい区間に分け、各区間から1つずつ時刻を選ぶため投稿が窓全体に散る。窓幅は回数で割り切れ、各区間が15分の倍数になること。その日の投稿時刻は日付・枠ID・区間番号から決まる決定論的な擬似ランダム（SHA-256シード、15分刻み）で、その日の全tickが同じ時刻に合意する。複数回の場合は解決後の枠IDに_1・_2…の接尾辞が付く。解決後の時刻は通常枠と同じく--dueの2時間回収・rkey重複照合・状態記録の対象になる。当日分の解決時刻と文面は引数なしのdry-runプレビュー（random slot表示）で確認できる。follower_recruitは窓09:00〜21:00・1日3回に設定している。

API応答は最大4MiBで読み、UTF-8・JSONオブジェクト・エラー応答の混入を検証する。認証のDIDとトークンの型、履歴の投稿種別・本文・タイムゾーン付き日時・自分のDIDを確認し、不正な履歴では投稿しない。投稿成功のURIは自分のDIDとapp.bsky.feed.postに限定し、CIDの型・空白も確認する。CIDのハッシュ内容までは再計算しない。APIのエラー本文をそのままログに出さず、定型コードだけ保持する。

日付・予定時刻・枠IDから同じTID形式のrkeyを生成し、投稿前にgetRecordで直接確認する。同時実行が事前照合をすり抜けても同じキーへcreateRecordし、競合時はそのキーを再読込する。putRecordによる上書きは行わず、別の本文がキーを使用している場合は停止する。最後の送信が通信エラーでも、保存済みかをもう一度照合して成否を決める。createdAtは実際の送信時刻を維持する。

旧方式のランダムキー投稿は、互換のため100件の文面・時間帯照合も行う。レコードキーから新しいcreatedAtの順序を保証する前提にはしない。新方式の同じキーの再確認は、この100件の走査に依存しない。設定のIDや予定時刻を変更するとキーも変わるため、変更をまたぐ自動再投稿の完全な抑止は保証しない。
