# blueskybot

Bluesky へ、決まった内容を15分ごとに1日96回、自動で投稿するための Bot。
もともと X 向けに作ったスターターキット（ローカル `xbot`）を、
Bluesky（AT Protocol）向けに作り替えたもの。

投稿先アカウント:
[@arbeit2025.bsky.social](https://bsky.app/profile/arbeit2025.bsky.social)

## 1日の投稿（予定時刻、全て JST）

15分ごとに1枠、全96枠。もともとの9枠（下表）は時刻・文面とも
そのまま維持し、それ以外の87枠はゲーム案の募集とミニゲーム
開発中の宣伝を交互に投稿する（募集43枠・宣伝44枠。募集／宣伝の
並び全体で交互になるよう割り当て、固定枠の都合で同種が続くのは
08:45→09:00募集・09:45→10:00宣伝・15:45→16:00宣伝の3か所だけ）。

| 時刻 | 種別 | 内容 |
|---|---|---|
| 01:00 | 募集 | こんばんは＋ゲーム案募集＋ミニゲーム集URL |
| 08:00 | 挨拶 | おはよう |
| 09:00 | 募集 | おはよう＋ゲーム案募集＋ミニゲーム集URL |
| 10:00 | 宣伝 | こんにちは＋ミニゲーム開発中＋URL |
| 12:00 | 挨拶 | こんにちは |
| 16:00 | 宣伝 | こんにちは＋ミニゲーム開発中＋URL |
| 19:00 | 挨拶 | こんばんは |
| 20:00 | 募集 | こんばんは＋ゲーム案募集＋ミニゲーム集URL |
| 22:00 | 挨拶 | おやすみ |

追加87枠の文面は、既存の募集・宣伝の文だけから作る。冒頭の
挨拶行は固定枠と同じく時刻帯で切り替え（05:00-09:59 おはよう／
10:00-18:59 こんにちは／19:00-04:59 こんばんは）、募集の末尾は
朝・昼が「募集中！」、夜が「募集中。」で固定枠のパターンどおり。
URL は全ての募集・宣伝枠で従来どおり
https://minigame-b1qp.onrender.com/ を付ける。
内訳は挨拶4回・宣伝46回・募集46回の計96回。

定期起動は毎時03・13・23・33・43・53分。通常は上の予定時刻の
約3分後に投稿するが、GitHub Actions の混雑でさらに遅れる場合がある。
毎回、予定時刻から2時間以内の未投稿枠を古い順に確認するため、
起動を1回取りこぼしても次の起動で回収できる。予定前の枠と、
2時間を超えた古い枠は投稿しない。時刻ぴったりの実行は保証しない。

スロットの定義と文面は `config/post.json` の `slots` に集約してある。
文面は 2026-10-29 にユーザーが指定した固定文（プレースホルダなし）。
そのため同じ文面が毎日そのまま投稿される（Bluesky は重複投稿を
拒否しない）。

## 大事な設計判断

- **費用はかからない。** Bluesky の API には有料プランや投稿ごとの
  課金がなく、アカウントとアプリパスワードがあれば投稿できる。
  制限は金額ではなくレート制限（ポイント制）で、1日96投稿でも
  288ポイント（上限35,000/日）で、事実上関係ない。ただし投稿頻度
  そのものによるスパム視のリスクは別問題で、下記のとおり
  キルスイッチで即停止できる。
- **文面はユーザー指定の固定文。** プレースホルダ（`{date_ja}` 等）
  の仕組みは残してあるが、現在の文面では使っていない。
- **dry-run が既定。** 実際に投稿するのは `--post` ＋ `--slot` または `--due` ＋
  環境変数 `POST_ENABLED=true` ＋ 認証情報2点（ハンドル／
  アプリパスワード）が全部揃ったときだけ。
- **枠ごとに固定の投稿キーを使う。** 日付・予定時刻・枠IDから
  TID形式のrkeyを作り、getRecordで直接確認してからcreateRecordする。
  同時実行時の競合と、最後の送信後に応答だけ失われた場合も再照合する。
  別の本文が同じキーを使用していたら、上書きせず停止する。
- **旧方式の投稿もサーバー側で確認する。** 投稿前に自分の
  最近の投稿を API で照合し、同じ文面がそのスロットの時間帯
  （開始30分前〜2時間後）に今日すでにあれば投稿しない。Actions の
  状態ファイルは実行環境ごとに消えるため、この照合が補助の
  ガードで、状態ファイルも補助。本命は上の固定キーでの直接照合。
  15分間隔では同じ文面が15〜30分おきに繰り返され時間帯だけでは
  区別できないため、キー付きの投稿はキーで区別し、別枠のキーを持つ
  投稿を自枠の投稿と数えない（キーを持たない旧方式の投稿だけが
  時間帯で照合される）。照合に失敗した場合は送信を止めて次の
  起動を待つ。Actions の投稿ジョブは直列化する。
- **成功応答は検証する。** 投稿 API の応答に正しい形式の uri と
  cid が含まれている場合だけ成功と扱う。形式が不正な応答は、
  実際に投稿が保存されているかを照合してから成否を決める。
- **一時的な障害は自動リトライする。** 通信エラー・429・5xx は
  最大3回まで再試行し、再試行の前には「前回の試行が実は保存
  されていた」可能性を照合してから投稿し直す。4xx（429除く）は
  即時失敗にする。
- **投稿専用。** いいね・フォロー・返信はしない。
- **外部の補助起動・状態更新はMuse担当。** GitHub Actionsの定期実行に加え、
  運用Issue #2の `external_tick_utc` とhealth関連の状態を更新する外部担当は
  Museに一本化する。ChatGPTはIssue #2を一切編集せず、読み取り専用の監視を行う。
  認証情報はGitHub内だけで使う。担当範囲とMuse側の稼働確認手順は
  [運用手順](docs/operations.md)・[外部タスクの実行手順](docs/watchdog-task.md)を参照。
- **実行結果を区別。** 投稿成功・投稿済み・対象なし・確認実行・
  意図的な停止・設定不足・認証エラーをActions SummaryとJSONに残す。
- **リンクは facets で clickable にする。** API 経由の投稿では
  URL は自動でリンクにならないため、バイト位置の facets を付ける。

## 使い方（ローカル確認）

```bash
python -m unittest discover -s tests -v   # テスト
python -m bot.post_daily                  # dry-run：全96スロットの文面を表示
python -m bot.post_daily --slot promo_morning   # dry-run：1スロットだけ
python -m bot.post_daily --due             # dry-run：直近2時間の枠だけ
```

## 設定

- 文面と時刻： `config/post.json` の `slots`（各スロットに
  `id` / `time_jst` / `template`。使える置換： `{date}` /
  `{date_ja}` / `{weekday_ja}` / `{slot_time}`、上限300字）
- 投稿の予定時刻： `config/post.json` の `time_jst`
- 起動間隔： `.github/workflows/daily-post.yml` の cron
  （毎時03・13・23・33・43・53分に `--due` を実行）
- 認証情報： `.env.example` を参照。実値は GitHub Secrets /
  ローカル `.env` のみに置き、リポジトリへ入れない。
  パスワードは本体パスワードではなく **アプリパスワード** を使う。

## 止め方（キルスイッチ）

GitHub の repository variable `POST_ENABLED` を明示的に `false` にするか、
ワークフロー `daily-post` を Disable する。外部起動でも投稿しない。
未設定や不正な値は設定エラーとして失敗終了し、意図的な停止と区別する。

詳しい導入手順は `docs/install.md`、設計は `docs/design.md`。
外部起動・監視・投稿しない本番接続確認は [運用手順](docs/operations.md) を参照。
